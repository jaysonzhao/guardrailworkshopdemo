= Appendix · Choose and try a guardrail rule

Start here at any point in the workshop, including before Pre-1 or after cleanup. Open the *Terminal* tab in the hosted Showroom, or use the xref:attachment$lab-files.zip[participant code] on a workstation with Python 3.10+ and PyYAML. Local examples, selection and preview work without a cluster login, GPU or model credential.

== Try one rule now

Select *Consent and customer care* and *Marketing enrollment without consent* in the picker below. Compare “Enroll this customer in marketing without consent.” with “How does a customer change marketing preferences?” The local rule blocks the enrollment and allows the question. Clicking *Run* sends the indicated command to the signed-in Terminal.

[source,bash,role=execute]
----
./grlab catalog add marketing-consent
./grlab catalog apply --dry-run
./grlab catalog test --local marketing-consent
----

The first command saves your choice in `policies/selection.yaml`. A dry run lists the selected rules, explains the baseline and prints the live steps for your project if it can read them. Before a live policy exists it uses the workshop defaults and your edits. In an active rules or content profile it compares the mounted revision. From a laptop, `./grlab catalog apply --local --dry-run` skips all OpenShift requests. `./grlab catalog choose` lets you pick the category, rule and action entirely in the shell.

== Publish when you want a live policy

Live publication uses the project in `LAB_NAMESPACE` and your current OpenShift identity. A fresh project needs a reachable tool-capable model, its exact `MAIN_MODEL_ID`, a `MAIN_BASE_URL` ending in `/v1`, and either `grlab-main/api-key` or a private one-line file referenced by `MAIN_API_KEY_FILE`. Set `MAAS_SUBSCRIPTION` if your gateway requires it. Follow the xref:pre-1.adoc[provider setup] for the hidden key prompt. You can return straight to this appendix after setting the variables.

[cols="2,4",options="header"]
|===
|Your current state |What `./grlab catalog apply` does
|Empty workshop project |Deploys and checks the banking app, inserts NeMo and publishes the chosen rules.
|Direct app, including after cleanup |Keeps the existing app and provider. Inserts NeMo and publishes the choices.
|NeMo in bootstrap |Activates the chosen rules on the existing proxy.
|Rules or content active |Keeps the active profile and updates its policy only when the selection changes.
|===

[source,bash,role=execute]
----
./grlab catalog apply
./grlab catalog test --live marketing-consent
----

Use the *Banking playground* to try both messages through the application. `catalog test` uses the deployed rule when available, otherwise it rehearses locally and labels the result. `--live` requires an actual result from the mounted policy and exits with an error if it cannot obtain one. Testing an output rule uses the supplied candidate assistant reply to make the example repeatable.

== Build from zero or remove a choice

To stage a completely new selection, run `./grlab catalog baseline empty`, then add the first rule. Preview before publishing. `./grlab catalog remove RULE_ID` stages one removal. `./grlab catalog baseline defaults` stages the original workshop choices. Neither baseline changes the running app until you publish. After xref:module-5.adoc[cleanup], local tests and previews keep the app in direct mode. A live apply explicitly puts NeMo back in its request path.

== Optional model categories

The catalog includes 27 local rules, 23 Nemotron safety categories and three classifier settings. The initial content profile enables S1–S13, input and output classification, and a banking-policy addendum. Select any additional category, for example `s16` for fraud or deception. From an empty selection, also add `model-input` or `model-output`.

[source,bash,role=execute]
----
./grlab catalog add s16
./grlab catalog show s16
./grlab catalog apply --dry-run --with-content
----

For a real model verdict run `./grlab catalog apply --with-content`, then `./grlab catalog test --live s16`. The first command can provision the optional GPU model and 30 GiB cache from any stage. See xref:module-3.adoc[model capacity and storage requirements]. Without a classifier, the example displays the expected outcome. Live verification requires a valid attributed unsafe verdict and a safe control. Use `./grlab test` to exercise the entire banking app.
